# Vault integration guide

This local integration demonstrates identity-specific access to Vault. It does not implement Member 4's renewal scheduler, workload injection, or post-quantum certificate lifecycle. See [architecture](vault_architecture.md) and the [API reference](vault_api_reference.md).

| Requirement | Current provision | Status / outstanding question |
|---|---|---|
| Application identity | `approle/` with one-use Secret IDs | Live Part 3 audit confirmed roles and bindings on 8 November 2026 |
| Application secret | `secret/` KV v2 | Real-server AppRole isolation tests passed; certificate manager has no KV access |
| Certificate request | `pki/sign/service-a-role` | Real-server ECDSA P-256 CSR demonstration passed; Member 4 format and algorithms need confirmation |
| Public CA / chain | `pki/cert/ca`, `pki/ca_chain` | Retrieved and checked on the real server; trusted distribution must be arranged |
| Revocation | `pki/revoke` | Administrator-only, not granted to certificate manager; Member 4's needs unconfirmed |
| Private key | Generated by requesting application | CSR is sent to Vault; private key stays with requester |
| Downstream delivery | Member 4's responsibility | Workload target, file format and delivery mechanism unconfirmed |

The only concrete Vault client prepared here is the local test client. No Member 4 certificate-management application or agreed interface was found in this workspace. A separate historical repository checkout contains `docs/week3-day2-vault-integration.md`, which recorded a blocked Minikube control plane and pending Vault integration; it does not establish current cluster status. Its `src/Key_rotation.py` concerns application encryption keys, not a verified Vault PKI integration. The certificate-manager policy grants signing under one role and reading the CA; it does not grant secret reads, unrestricted PKI, or revocation. A different application must use a separately authorized identity; do not combine permissions just for a demonstration.

Run the read-only audit with `python scripts/vault_integration_audit.py`; the administrator token is entered at a hidden prompt. The integration demonstration, `python scripts/vault_integration_demo.py`, uses the administrator token only to generate one-use test credentials and clean up its disposable test certificate/token. Application operations use separate short-lived AppRole tokens. It prints status and HTTP codes, never credentials or secret values, and writes sanitized output to ignored `.tmp/`. It does not initialize Vault, create mounts, change policies, or overwrite CA material. It is explicitly local HTTP only and does not implement HTTPS; replace the transport with validated HTTPS before use beyond localhost.

Connection errors and timeouts are reported without echoing request data; 403 means denied and 404 can mean missing or deleted data. Do not silently retry unauthorized requests. Use protected channels or response wrapping for Secret IDs, which are one-use and expire after 10 minutes. Tokens have a 10-minute TTL and 15-minute max; CIDR restrictions limit them to loopback. The exact client, format, trust distribution, algorithm, revocation duties and remote deployment remain for Member 4 to confirm.

Vault 2.2 documents ML-DSA X.509 support, but only conventional ECDSA P-256 has been tested in this deployment. ML-KEM is key establishment, not a certificate signature. See [PKI details](vault_pki_configuration.md); do not claim ML-DSA interoperability before a real client and certificate test.
