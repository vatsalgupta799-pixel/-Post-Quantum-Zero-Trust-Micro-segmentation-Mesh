# Vault PKI demonstration and PQC compatibility

A root CA is a trust anchor; an intermediate CA is signed by a root and can issue leaves while the root remains offline. A certificate role restricts names, key types and lifetimes. Certificates have expiration times, and renewal or replacement obtains a new certificate. Revocation makes a certificate invalid before expiry for clients that actually check revocation; the chain connects a leaf to its trusted issuer.

On 5 November 2026 the real Vault server was configured with a **single online local demonstration root**, not an offline root/intermediate production architecture. The `pki/` mount has a 168-hour maximum TTL and an internal ECDSA P-256 CA with a 168-hour lifetime. Its private key stays in Vault. Role `service-a-role` is limited to the exact DNS name `service-a.mesh.test`; subdomains, wildcards, arbitrary domains and IP SANs are disabled. The role uses EC P-256, with a one-hour default and 24-hour maximum TTL. CA and CRL URLs use `127.0.0.1` and work only for the local machine.

The private setup script generated an EC P-256 private key in process memory and sent only its CSR to `pki/sign/service-a-role`. It verified the returned certificate's common name, DNS SAN, and direct CA signature; the certificate was valid from 2026-11-05 11:40:12 UTC to 12:40:42 UTC. It revoked that certificate, verified the CA signature on the CRL, and found the certificate's serial in it. The test did not demonstrate a client enforcing the CRL. The temporary leaf private key was neither printed nor saved; actual consumers must generate and securely retain their own keys. The Vault `issue` endpoint instead returns a generated private key to its caller; that caller must protect it, because Vault does not retain the leaf private key for later retrieval.

The CA certificate is available from `http://127.0.0.1:8200/v1/pki/ca` when Vault is running and unsealed. The online demo root expires approximately seven days after creation; plan replacement before expiry and do not use it for production or remote clients. The script's `pki` phase will not overwrite an existing mount and must not be rerun against this CA.

HashiCorp's [Vault 2.2 release notes](https://developer.hashicorp.com/vault/docs/updates/release-notes) state that the PKI engine supports ML-DSA X.509 certificates; the [PKI API](https://developer.hashicorp.com/vault/api-docs/secret/pki) documents RSA, EC, Ed25519 and ML-DSA, with ML-DSA-44/65/87 parameter sets. Only ECDSA P-256 was tested here; ML-DSA issuance, chain validation and client compatibility were **not tested**. HashiCorp notes ML-DSA cannot be used with OCSP or ACME in its current implementation. ML-KEM is a key-encapsulation algorithm, not a certificate signature. Hybrid TLS key exchange is distinct from ML-DSA certificates. Member 4 must verify the selected client, certificate format and signing workflow before integration; an external issuer may be needed if that workflow is unsupported. No automated rotation is implemented.
