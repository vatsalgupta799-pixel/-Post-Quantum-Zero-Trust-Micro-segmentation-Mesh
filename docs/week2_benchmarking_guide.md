# Week 2: Real TLS Handshake Benchmarking Guide

## Purpose

Week 2 compares fresh TLS 1.3 connections that negotiate either X25519 or the
hybrid X25519MLKEM768 named group. It is separate from the existing Day 5
benchmark: Day 5 measures local Python cryptographic operations, not TLS,
Envoy, certificates, Kubernetes networking, or service-mesh performance.

The Week 2 harness uses a compatible `openssl s_client` process for every
measured connection. Python orchestrates the run and analysis, while OpenSSL
provides the TLS 1.3, certificate-validation, and negotiated-group evidence.
This makes the metric **connection-establishment latency including client
process startup and exit**, not a pure in-library handshake timer. A run fails closed
unless each sample confirms TLS 1.3, certificate validation, and the expected
named group. Listing a group in a configuration is not evidence that it was
selected.

The earlier smoke files predate hostname verification; they establish group
capability but do not establish that the certificate matched the intended
hostname. New runs verify the name as well as the certificate chain.

## Current Baseline

**Classical (X25519):** A 1,000-connection configuration-restricted baseline
is retained with p50 15.36 ms, but it does not contain direct group telemetry.
It cannot be used as a verified classical-versus-hybrid comparison. See
[the Week 2 benchmark report](week2_benchmark_report.md) for the limitation.

**Hybrid (X25519MLKEM768):** Python's OpenSSL 3.0.18 backend remains unable
to configure this group. A separate OpenSSL 4.1.0 CLI now provides the actual
TLS client and server capability; a certificate-validated, three-sample local
smoke test negotiated the group on every attempt. See
`results/week2/openssl41-local-smoke/`. This is a capability smoke test, not
a full benchmark or an Envoy result.

## Required Inputs for a Live Run

### For the classical experiment

1. A reachable TLS 1.3 server endpoint and port.
2. A CA file for certificate validation. For local tests, the self-signed
   certificate generated by `scripts/local_tls_server.py` is sufficient.
3. The server must support TLS 1.3 with X25519.

### For the hybrid experiment (requires team coordination)

1. A TLS 1.3 server that supports X25519MLKEM768. This requires either:
   - Envoy built with BoringSSL (evidence shows Envoy 1.41.0-dev works), or
   - OpenSSL 3.5+ with hybrid group support enabled.
2. A compatible `openssl s_client` that reports the negotiated group; pass
   its executable path to `--openssl-path`. Python orchestrates the client.
3. A trusted CA file and, for mTLS, client certificate and key.

## Quick Start — Local Classical Test

### Step 1: Start the local TLS server

```powershell
python scripts/local_tls_server.py --port 18443 --group X25519
```

This generates a self-signed certificate at `.tmp/tls-test/cert.pem`.

## Local Hybrid Smoke Test with OpenSSL 4.1+

Python's `ssl` module cannot host this group on the current interpreter. Use
the compatible OpenSSL executable for both ends instead:

```powershell
$openssl = "C:\Program Files\OpenSSL-Win64\bin\openssl.exe"
$certDir = ".tmp\openssl-hybrid"
New-Item -ItemType Directory -Force -Path $certDir | Out-Null
& $openssl req -x509 -newkey rsa:2048 -sha256 -nodes `
  -keyout "$certDir\key.pem" -out "$certDir\cert.pem" -days 1 `
  -subj "/CN=localhost" -addext "subjectAltName=DNS:localhost,IP:127.0.0.1"
& $openssl s_server -accept 18444 -cert "$certDir\cert.pem" `
  -key "$certDir\key.pem" -tls1_3 -groups X25519MLKEM768 -www
```

In another terminal, verify and smoke-test it:

```powershell
python scripts/verify_tls_group.py --mode hybrid --host 127.0.0.1 --port 18444 `
  --server-name localhost --ca-file .tmp\openssl-hybrid\cert.pem `
  --use-openssl --openssl-path $openssl
python scripts/benchmark_tls.py --mode hybrid --host 127.0.0.1 --port 18444 `
  --server-name localhost --ca-file .tmp\openssl-hybrid\cert.pem `
  --openssl-path $openssl --warmup 3 --iterations 10 `
  --output-dir results\week2\openssl41-local-hybrid-smoke
```

The benchmark's timer includes OpenSSL client process startup, TCP setup, and
direct verification. Keep it separate from a future Envoy experiment.

### Step 2: Verify the TLS group with a compatible OpenSSL CLI

```powershell
$openssl = "C:\path\to\openssl.exe"
python scripts/verify_tls_group.py --mode classical --host 127.0.0.1 --port 18443 --server-name localhost --ca-file .tmp/tls-test/cert.pem --use-openssl --openssl-path $openssl
```

The script must report `TLSv1.3`, `Verification: OK`, and the actual `X25519`
group. If it cannot, stop: the run is not valid evidence.

### Step 3: Run a smoke test

```powershell
python scripts/benchmark_tls.py --mode classical --host 127.0.0.1 --port 18443 --server-name localhost --ca-file .tmp/tls-test/cert.pem --openssl-path $openssl --warmup 3 --iterations 10 --timeout 10 --output-dir results/week2/classical-smoke
```

Inspect `raw.csv` and `verification.json`. Every successful row must show the
actual group, `certificate_verified=True`, and `session_reused=False`.

### Step 4: Run the full experiment

```powershell
python scripts/benchmark_tls.py --mode classical --host 127.0.0.1 --port 18443 --server-name localhost --ca-file .tmp/tls-test/cert.pem --openssl-path $openssl --warmup 100 --iterations 1000 --timeout 10 --output-dir results/week2/classical-verified
```

## Running Against an External TLS Endpoint

Replace the host, port, server name, and CA file with team-provided values:

```powershell
$python = python

# Verify first
& $python scripts/verify_tls_group.py --mode classical --host tls-benchmark.example.test --port 8443 --server-name tls-benchmark.example.test --ca-file /path/to/trusted-ca.pem --use-openssl --openssl-path /path/to/openssl

# Benchmark
& $python scripts/benchmark_tls.py --mode classical --host tls-benchmark.example.test --port 8443 --server-name tls-benchmark.example.test --ca-file /path/to/trusted-ca.pem --openssl-path /path/to/openssl --warmup 100 --iterations 1000 --timeout 10 --output-dir results/week2/classical-verified
```

For the hybrid test (requires OpenSSL 3.5+ or BoringSSL support):

```powershell
& $python scripts/verify_tls_group.py --mode hybrid --host tls-benchmark.example.test --port 8443 --server-name tls-benchmark.example.test --ca-file /path/to/trusted-ca.pem --use-openssl --openssl-path /path/to/openssl

& $python scripts/benchmark_tls.py --mode hybrid --host tls-benchmark.example.test --port 8443 --server-name tls-benchmark.example.test --ca-file /path/to/trusted-ca.pem --openssl-path /path/to/openssl --warmup 100 --iterations 1000 --timeout 10 --output-dir results/week2/hybrid-verified
```

For mTLS, add `--client-cert /path/to/cert.pem --client-key /path/to/key.pem`
to both commands.

## Using openssl s_client for Better Verification

Use a compatible OpenSSL CLI for verification and for every benchmark sample:

```powershell
& $python scripts/verify_tls_group.py --mode hybrid --host HOST --port PORT --ca-file CA --use-openssl --openssl-path /path/to/openssl
```

This parses the negotiated-group output from OpenSSL. The benchmark repeats
the same direct check for each sample; it also uses `-no_ticket` and a new
process per connection to separate the full-handshake experiment from session
resumption.

## Analyze Raw Data

Pass verified raw CSV files to the analysis script:

```powershell
python scripts/analyze_tls_results.py --classical-csv results/week2/classical-verified/raw.csv --hybrid-csv results/week2/hybrid-verified/raw.csv --output-dir results/week2/comparison-new
```

This produces:
- `combined_summary.csv` — summary statistics for both modes.
- `comparison.json` — absolute and relative differences.
- `percentile_comparison.png` — bar chart of p50, p95, p99, and mean.
- `latency_cdf.png` — empirical cumulative distribution.
- `latency_boxplot.png` — box plot comparison.
- `comparison_report.md` — full markdown report.

## Interpreting the Percentile Metrics

| Metric | Meaning |
| --- | --- |
| p50 | Median — 50% of connections complete faster than this |
| p95 | 95th percentile — only 5% of connections are slower |
| p99 | 99th percentile — only 1% of connections are slower |
| Mean | Arithmetic average — sensitive to outliers |
| Std dev | Dispersion — how spread out the latencies are |

Relative overhead is calculated as:

```
Overhead (%) = ((hybrid_latency - classical_latency) / classical_latency) × 100
```

A positive value means hybrid is slower. A negative value would mean hybrid
is faster (unexpected but possible due to measurement noise).

## Reproducing on Another Machine

1. Clone the repository and install dependencies:
   ```bash
   python -m pip install -r requirements.txt
   ```

2. Run the environment checker:
   ```bash
   python scripts/check_environment.py
   ```

3. Check OpenSSL version for group support:
   ```python
   import ssl
   print(ssl.OPENSSL_VERSION)
   ctx = ssl.SSLContext(ssl.PROTOCOL_TLS_CLIENT)
   ctx.set_ecdh_curve('X25519MLKEM768')  # Raises if unsupported
   ```

4. Follow the Quick Start steps above.

5. Ensure the same warmup count, iteration count, timeout, and concurrency
   for both modes. The only variable that should differ is the key-exchange
   group.

## Interpretation and Limits

The current timing includes OpenSSL process startup, TCP setup, TLS handshake,
verification, and process exit. It is **connection-establishment latency**,
not pure TLS handshake latency. Both modes must use the same boundary.

A completed run describes only the stated endpoint, hardware, versions, path,
and workload. It does not establish production capacity or performance of
unrelated OPA, Kubernetes, or service-mesh controls. Packet capture and CPU
measurements are optional; collect them only for authorized test traffic and
label them as observed measurements rather than theoretical key-share sizes.
